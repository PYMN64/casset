# S0.1 — Repository & Environment Baseline

**Baseline date:** 2026-08-08
**Repository:** PYMN64/casset
**Baseline branch:** `baseline/pre-s0.1-2026-08-08`
**Primary branch:** `master`
**Application framework:** Django 6.0 (declared by `config/settings.py` and generated project header)
**Python version:** Not declared in repository baseline
**Database:** SQLite in current settings
**Environment/dependency manifest:** No `requirements.txt`, `pyproject.toml`, `pytest.ini`, or `Dockerfile` found at repository root

## Baseline conclusion
The repository is a viable Django modular-monolith foundation and should be stabilized rather than rewritten. The current code already contains meaningful MVP domains, but several boundaries are incomplete or internally inconsistent. No production code is changed by this baseline report.

## Application map
- `accounts` — identity, onboarding, creator lifecycle, profile and OTP foundations.
- `tracks` — genres, tags, albums and tracks; track lifecycle and media fields.
- `uploads` — upload workflow/views; model layer currently empty.
- `plays` — play events, daily statistics, fraud flags and playback endpoints.
- `moderation` — reports and audit log.
- `explore` — discovery/featured content foundation.
- `interactions` — likes, follows, favorites and comments.
- `playlists` — playlists and playlist items.
- `billing` — plans, invoices, transactions and payout requests.
- `subscriptions` — separate plan/subscription implementation; overlaps billing.
- `core` — platform-wide settings and shared primitives.

## KEEP
1. Modular Django monolith as the MVP architecture.
2. Existing domain separation across accounts/tracks/plays/moderation/interactions/etc.
3. Track lifecycle states (`draft`, `submitted`, `approved`, `rejected`, `takedown`, `blocked`) as the basis for moderation.
4. PlayEvent uniqueness constraint and hashed IP/UA approach as a starting anti-abuse mechanism.
5. DailyTrackStat as a derived analytics structure.
6. FraudFlag as an initial soft-signal mechanism.
7. Moderation AuditLog.
8. Existing creator/public-profile foundations and OTP data model.

## REFACTOR
1. Extract playback qualification from `plays/views.py` into an explicit service/domain layer.
2. Extract upload validation/lifecycle logic from `uploads/views.py` into an upload service boundary.
3. Replace direct reward mutation of `UserProfile.points` with an auditable `PointLedger`.
4. Consolidate billing/subscription concepts into one canonical entitlement model path; do not delete either app until migration impact is mapped.
5. Separate derived counters/aggregates from authoritative event/ledger data.
6. Move complex creator analytics queries out of `accounts/views.py` into analytics services/query modules.
7. Establish a canonical media/storage abstraction before production object storage.

## FIX
1. `uploads` is referenced by `config/urls.py` but is absent from `INSTALLED_APPS`; verify and correct application registration before relying on its templates/static/models/migrations.
2. Current playback reward flow trusts a client-provided progress value; this is not sufficient proof of a qualified play.
3. `UserProfile.points` is currently mutated directly from the playback endpoint and is not an auditable ledger.
4. `accounts/views.py` contains broad business logic and should not remain the long-term location for creator analytics and lifecycle decisions.
5. Production settings are not ready: SQLite is the active database; default secret/salt fallbacks are insecure; DEBUG defaults to enabled.
6. Dependency management is not reproducible because a repository-level dependency manifest was not found.
7. Automated test infrastructure is not established through a repository-level pytest configuration.
8. Media is configured through local `MEDIA_ROOT`; production object storage must be introduced behind an explicit storage boundary.
9. `subscriptions` and `billing` both define plan/subscription concepts, creating a canonical-source risk.

## REMOVE / CONSOLIDATE
No application should be deleted during S0.1. The correct action is to map dependencies first. Likely future consolidation target: `subscriptions` into the canonical billing/entitlement path, but only after migration and runtime references are audited.

## DEFER
- Microservices/distributed architecture.
- Advanced recommendation/AI recommendation.
- Complex payout automation and payment-gateway completion.
- Chat and advanced social systems.
- Kubernetes and premature infrastructure complexity.
- Aggressive performance optimization before measurement.

## Critical MVP risk order
1. Trustworthiness of Qualified Play and reward accounting.
2. Reproducible dependencies and test foundation.
3. Production database/media configuration.
4. Billing/subscription canonicalization.
5. Service boundaries around upload/play/reward.

## S0.1 acceptance result
**PASS WITH CRITICAL FOLLOW-UP.** The repository is suitable to continue. It is not yet release-ready and should not receive broad feature expansion before S0.2/S0.3 foundation work.
